- `src/styles.css` — shared design tokens, button hierarchy, layout, responsive rules.

## Availability slots

A published slot is an object, not a bare time string:

```js
{ time: '11:00', mode: 'Offline', location: 'Library study zone, 2nd floor', duration: 90 }
```

- `location` is always `''` for an Online slot, and always set for an Offline one. `makeSlot()` enforces that, so a room can never be attached to an online session.
- `slotKey(slot)` (`time|mode`) is a slot's identity. It is used to de-duplicate published and tutor-added slots and to remove one by reference.
- Every tutor's schedule is generated by `buildAvailability()` from `SCHEDULE_SEED` in `mockData.js`, with a per-tutor `offlineRatio`. That is why some tutors are online-only and some are mostly in person. The generator is seeded, not `Math.random()`, so the demo and the tests are reproducible; change `SCHEDULE_SEED` to reshuffle everything.
- `ensureBothModes()` repairs an unlucky draw so a tutor who may teach in person always has at least one offline slot.
- `modesFor()` derives what a tutor advertises, so a tutor never claims a format they have no slot for.
- Seeded requests are attached to slots that really exist (`pickSlots`), and a custom-time request is placed on a time the tutor never published so a student is never shown as double-booked.

## State ownership

- `App.jsx` holds the single `requests` array and the single `sessions` array. There is no second, role-specific copy.
- `visibleRequests` is a `useMemo` that filters that one array by the current user: a tutor sees requests for `user.tutorId`, a student sees only their own.
- Every route receives `visibleRequests`. Nothing passes the raw `requests` array to a page.
- `createSession` (booking) and `requestAction` (accept/decline/suggest) both write to that same array, so a page never has to be told about a change twice.
- Tutor-added availability also lives in `App` state as slot objects, and is merged with the generated schedule when a student books.
- Only the user, theme, accent, and sidebar state are persisted to `localStorage`. Requests, sessions, and availability reset to the seed data on reload by design.

### Availability has one owner

`TUTORS[].availability` in `mockData.js` is a **seed**, not live state. `App` copies it in once with `seedAvailability(TUTORS)` and every page reads that one copy through the `availability` prop:

```js
const [availability, setAvailability] = useState(() => seedAvailability(TUTORS));
```

`seedAvailability` deep-copies each slot, so editing the live copy can never rewrite the fixture the tests read.

This matters because the two halves of the Availability screen used to read different things: the agenda came from the static seed while the open-slots panel and the week strip counted only session additions. The result was a page that listed three published hours beside a panel reading "No open slots". One owner means a published slot is also removable, a removed slot disappears everywhere at once, and the panel can never contradict the agenda.

No page should read `tutor.availability` directly for display. `AvailabilityPage`, `TutorDetailPage`, `FormPage`, and `CalendarWorkspace` all take `availability` from `App`.

## Published slots vs custom time

- A published slot is locked: the student sees the slot's own mode and room, and cannot change either. The UI shows a `.locked-schedule-note` instead of the controls.
- A custom-time request is fully editable: the student may pick Online or Offline and must supply a room for Offline.
- `selectedSlot` resolves the chosen published slot; `effectiveMode` and `effectiveLocation` are derived from it (or from the student's choice for a custom request), so the live summary, the validation, and the submitted payload cannot disagree.
- A `?time=` in the URL that the tutor no longer publishes is refused rather than booked, because there would be no mode or room to fall back on.
- `chooseSchedule()` and `chooseMode()` clear mode, location, and the schedule-specific time when the schedule kind or format changes, so a room typed for one arrangement cannot leak into another.
- The mode and room are stored on the **request** as well as the session, so a tutor can see where an in-person booking happens before accepting it.

## Request id handling

- `/booking?mode=suggest&request=<id>` and `/booking?mode=review&request=<id>` look the request up by exact id.
- If the id is missing or not in `visibleRequests`, the form renders a "Request not found" / "Suggestion not found" empty state. There is no fallback to the first request in the list.
- `requestAction` copies across only `date`, `time`, and `alternative`, and stores a tutor's reply as `suggestion`. It used to spread the whole `details` object onto both the request and the session, which overwrote the student's own `request.message` and left the request and the session describing the same booking differently.

## Confirming before anything is sent or destroyed

A single click should never destroy something, and it should not send something either. `ConfirmDialog.jsx` is the one confirm/cancel step, used in two groups.

### Destructive, and not recoverable from the other screen

| Action | Where | Reversible afterwards? |
| --- | --- | --- |
| Decline request | `RequestsPage` | No — the student has no cancel button |
| Cancel a suggested request (student) | `RequestsPage` | No — the tutor must reschedule |
| Remove availability slot | `CalendarWorkspace` | Yes — Undo in the same panel |
| Log out | `AppShell` | No — session state is lost |

### Sends, where the other person has already acted on a decision

| Action | Where | What the dialog shows |
| --- | --- | --- |
| Submit a booking request | `FormPage` → `BookingForm` | Tutor, subject, topic, date · time, mode, room, and whether it is a published slot or a custom request |
| Send another time | `FormPage` → `SuggestTimeForm` | Student, subject, the time it replaces, the new time, the optional backup, and the message |
| Accept a suggested time | `FormPage` → `ReviewSuggestionForm` | Tutor, subject, the confirmed time, mode, room, and the backup that is being dropped |

Each of these validates first and only opens the dialog once the form is otherwise sendable, so a review step never appears in place of a real error. The dialog is `tone="default"` because nothing is being destroyed, only sent. Cancelling calls the same state-clearing handler the Escape key does and touches none of the form fields, so the student or tutor lands back on their half-typed form.

Accepting a request from `RequestsPage` deliberately stays a single click, because that is the tutor granting what the student already asked for and the student can still cancel afterwards.

The dialog itself:

- `role="dialog"` with `aria-modal="true"`, and the title and description wired up with `useId`, so a screen reader announces the context rather than just "dialog".
- The description is a `div`, not a `p`, because the sending flows pass a review summary into it and a block-level table is not valid inside a paragraph.
- Focus starts on **Cancel** and Tab is wrapped between the two buttons. This is the important detail: these dialogs exist because a reflexive Enter was sending things, so the same reflex must not press the button for the user. Enter on a freshly opened dialog dismisses it.
- Escape and a click on the backdrop both cancel.
- On close, focus returns to whatever opened it, so a keyboard user is never dropped at the top of the page. If that control has since been removed (normal after deleting a row) the restore is skipped instead of throwing.
- `onCancel` is held in a ref so the effect only depends on `open`. Depending on an inline arrow from the parent would rebuild the listeners on every render and yank focus back mid-interaction.

Undo lives next to the notice it belongs to rather than in a global snackbar, so the message and the reversal cannot drift apart. `undoRemove` re-adds the stored slot object, which keeps the mode, room, and duration intact.

## Pressing Enter

`blockImplicitSubmit` in `src/lib/forms.js` is attached to the publish, booking, suggest-another-time, and profile forms. A browser submits a form when Enter lands in a single-line field, which meant a slot, a request, a suggestion, or a profile save could be sent without ever touching the button.

```js
export function blockImplicitSubmit(event) {
  if (event.key !== 'Enter') return;
  if (event.shiftKey || event.ctrlKey || event.metaKey || event.altKey) return;
  const { target } = event;
  const tag = target?.tagName;
  if (tag === 'TEXTAREA' || tag === 'BUTTON' || tag === 'A' || target?.isContentEditable) return;
  event.preventDefault();
}
```

The guard deliberately lets through a newline in a textarea, Enter on a focused button (which already activates), and Enter on a link, so it removes an accident rather than breaking keyboard use. Search and sign-in keep implicit submission, because there Enter is what the user wants.

## Giving every control an outcome

- A button must never look broken. `CalendarWorkspace`'s old "Manage availability" button called `navigate('/availability')` while already on `/availability`, so it was a no-op. It now takes an `onAddSlot` callback: `AvailabilityPage` passes a handler that scrolls to and focuses the publishing form, and any other caller still falls back to navigating.
- `addAvailability` in `App.jsx` silently ignores a slot that is already published, which is correct for state but invisible to the user. Both publishing forms therefore check `slotKey` first and report the duplicate as an error.
- Publishing confirms with a `.form-success-inline` message naming the time, format, room and date. Removing a slot writes a `.open-slot-notice` in the open-slots panel. Both use `role="status"`, and errors use `role="alert"`, so the outcome is announced rather than only shown.
- Switching day, week, or format clears the previous message, so a stale confirmation cannot be mistaken for the result of the last action.

## React concepts to be ready to explain

- `useState`: stores values that change while the page is open, such as form fields and current user.
- `useEffect`: runs side effects when a value changes, such as syncing theme/user preferences to localStorage.
- Props: data/functions passed from a parent component into a child component.
- `map()`: turns arrays such as tutors, requests, or navigation items into repeated UI.
- `key`: gives repeated React elements a stable identity when an array is rendered.
- `onChange`: updates controlled form state whenever an input changes.
- `preventDefault()`: stops a form from reloading the page before the React handler finishes.
- React Router: changes pages without a full browser reload and keeps the URL meaningful.

## Button hierarchy

- `.primary-button` — the one main action in a section.
- `.secondary-button` / `.ghost-button` — useful adjacent actions that should not compete with the primary CTA.
- `.text-button` / `.text-link` — low-emphasis navigation or optional actions.
- `.icon-button` — compact contextual controls such as close, previous/next, or notifications.
- `.danger-button` — destructive actions only.
